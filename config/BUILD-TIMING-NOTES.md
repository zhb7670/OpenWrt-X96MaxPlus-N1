# 编译耗时与 ccache 真相（实测记录）

> 本文档记录 X96MaxPlus-N1 源码编译的**真实耗时数据**，避免重复误判工期。
> 最后更新：2026-10-03

---

## 一、核心结论（血泪教训）

**ccache 不等于"第二次编译就飞快"。**

网上的说法"第一次 4h，有 ccache 后 30min"**仅适用于「编译成功过一次」的场景**。
如果**第一次编译中途失败**，ccache 只保存到**失败点之前的产物**，
失败点之后的包**仍然要全新编译**。

---

## 二、实测数据

| 项目 | 数据 |
|---|---|
| 首次冷编译（run 37086337377） | **4小时26分**（01:11 → 05:17，挂 kmod-oaf） |
| ccache 累积 | 1.0 GiB / 61917 次调用 |
| **ccache 命中率** | **14.05%**（Hits 8698 / Cacheable 61917） |
| 第二次（run 37126509756） | 仍预计 **3.5-4 小时** |

### 为什么命中率只有 14%？

ccache **只缓存 C/C++ 源码编译**，以下环节**完全不受益**：

| 环节 | 是否被 ccache 加速 |
|---|---|
| 源码/软件包下载 (dl/) | ❌ |
| autoconf / configure 检查 | ❌ |
| **Linux 内核编译** | ❌（内核用自己的 ccache 配置，且配置阶段占大头） |
| **LTO 链接** (`-flto=auto`) | ❌ |
| **Go 程序**（xray/mihomo/sing-box/docker 等） | ❌ Go 有自己的构建缓存 |
| Rust 程序 | ❌ |
| 打包 / 压缩 / 生成镜像 | ❌ |
| C 源码编译 | ✅ **只有这部分** |

**本项目里有大量 Go 程序**（OpenClash 的 mihomo、PassWall 的 xray-core、
Docker 的 dockerd/containerd、Alist、frp、gost…），这些**都不吃 ccache**。

## 三、正确的耗时预期

| 场景 | 预期耗时 |
|---|---|
| 首次冷编译（从零） | **4-5.5 小时** |
| 编译成功过 + 之后无变更 | 20-40 分钟 |
| **上次失败在 3.5h 处 + 本次重跑** | **3.5-4.5 小时**（不是 30 分钟！） |
| 成功基线 + 只改 1 个插件 | 15-30 分钟 |

---

## 四、如何真正实现"快速更新"（用户核心诉求）

**关键：必须先拿到一次「编译成功」的基线。**

一旦成功：
1. ccache 命中率会显著提升（因为所有包都编过了）
2. 后续只改动的包会重编，其余全部命中缓存
3. 单纯的小改动 → **15-30 分钟出包**

**所以策略是**：不惜代价跑完第一次完整编译，哪怕是分几次续跑。

## 五、超时防护机制（已实施）

| 层级 | 设置 | 作用 |
|---|---|---|
| job | `timeout-minutes: 355` | 防 GitHub 6h 硬杀 |
| step | `timeout-minutes: 330` | 5.5h 中断 |
| 命令 | `timeout --signal=SIGINT --kill-after=120s 320m make ...` | **5h20m 主动退出**（核心） |
| ccache 保存 | `actions/cache/save` + `if: always()` | **超时也保存缓存** |
| 缓存 key | `openwrt-<repo>-<source_hash>-<run_id>` | 每次更新，不冲突 |

**恢复逻辑**：`restore-keys: openwrt-lede-` 前缀匹配 → 下次能拿到最近一次的缓存。
